# Accounting journal entries migration contract

## Contract state

This is a planning contract only. No extractor, CLI block, plan format, target
writer, or reconciliation implementation exists yet. The service remains
`planned` and `executable: false`.

The separate Fineract-side service requirement for generating new monthly
journal numbers and reserving exact imported numbers is maintained in
[`FINERACT_MONTHLY_GL_JOURNAL_NUMBERING_REQUIREMENTS.md`](../../../../../docs/FINERACT_MONTHLY_GL_JOURNAL_NUMBERING_REQUIREMENTS.md).

## Source identity and scope

The authoritative Arissto journal header identity is:

```text
(CNT_PARTIDAS.ID_EMPRESA,
 CNT_PARTIDAS.ID_SUCURSAL,
 CNT_PARTIDAS.ID_PERIODO,
 CNT_PARTIDAS.ID_PARTIDA)
```

Each line extends that identity with
`CNT_DETALLE_PARTIDAS.ID_DETALLE_PARTIDA`. The future extractor must join on
the complete declared key; neither `ID_PARTIDA` nor `NUMERO_PARTIDA` may be
used alone as the migration identity.

Initial source tables:

| Source | Role |
|---|---|
| `CNT_PARTIDAS` | Journal header, business number, date, type, status, module, close, description, and user provenance |
| `CNT_DETALLE_PARTIDAS` | Posting account, debit/credit amount, concept, movement, bank-book, voucher, and auxiliary references |
| `CNT_PERIODO` | Accounting year/month and close state for `ID_PERIODO` |
| `CNT_CATALOGO_CUENTAS` | Source posting-account code and metadata used to resolve the bootstrapped Fineract chart of accounts |
| `CNT_TIPO_PARTIDA` | Source journal-type labels, including annual liquidation |
| `CIERRE_DIARIO` | Source operating date and close context; not a target sequence generator |

`CNT_MAYOR`, `CNT_MAYOR_DIARIO`, and `CNT_MAYOR_ANUAL` are reconciliation or
reporting evidence. They are not independent transaction sources and must not
be replayed as journal entries.

## Arissto journal-number contract

Arissto does **not** use an annual-only journal-number reset. The verified
business number `CNT_PARTIDAS.NUMERO_PARTIDA` follows a monthly accounting
period pattern:

```text
YYYYMM####
```

The four-digit suffix restarts at `0001` for each populated monthly accounting
period. Annual-liquidation journals (`ID_TIPO_PARTIDA = '003'`) use the
ordinary December sequence; year-end closure does not create a separate annual
numbering namespace.

The source contains reviewed back-period/date exceptions. Therefore the engine
must preserve `RTRIM(NUMERO_PARTIDA)` exactly as stored. It must not regenerate
the value from `FECHA_PARTIDA`, `CNT_PERIODO.ANIO/MES`, row order, or a target
counter. The detailed source evidence is maintained in
[`contabilidad-libro-mayor-y-partidas.md`](../../../../../../credesal-db-space/docs/learnings/contabilidad-libro-mayor-y-partidas.md#numeración-que-se-reinicia-por-período).

## Fineract identity and `ref_num` decision

Fineract stores GL debit and credit lines in `acc_gl_journal_entry` and groups
the lines of one accounting transaction by `transaction_id`.

| Arissto source | Fineract target | Contract rule |
|---|---|---|
| full journal key | durable migration crosswalk plus one target `transaction_id` | Idempotency authority; exact target representation is pending writer selection |
| `NUMERO_PARTIDA` | `acc_gl_journal_entry.ref_num` | Preserve exact trimmed source value on every target line in the transaction group |
| `FECHA_PARTIDA` | journal transaction/entry date | Preserve source business date, subject to target closure validation |
| detail `ID_CUENTA` | `acc_gl_journal_entry.account_id` | Resolve by reviewed source account code to the bootstrapped Fineract GL account |
| detail `DEBE`/`HABER` | debit/credit entry type and amount | Emit exactly one non-zero side per normalized target line unless an approved aggregation rule says otherwise |
| header/detail concepts | description/comments | Preserve within target length and privacy constraints; truncation must be deterministic and reported |

`ref_num` is the correct native field for the human-readable Arissto journal
number because it is an optional journal reference rather than Fineract's
technical grouping identity. It is not unique and cannot be the sole migration
key. The engine must not replace Fineract `transaction_id` with the Arissto
monthly number, reset a Fineract database sequence, or derive target row IDs.

For API-created manual journals, Fineract currently generates
`transaction_id`; the request supplies `referenceNumber`, which is persisted as
`ref_num`. If the standard API is selected, the engine must durably map the full
source journal key to the returned Fineract transaction ID and recover safely
when a response is lost after target commit.

## Accounting ownership and duplicate prevention

This service must not blindly replay every `CNT_PARTIDAS` row. Existing
migration services create native Fineract transactions whose accounting is then
generated by Fineract. Importing the corresponding Arissto GL journal would
double the economic effect.

Before implementation, a reviewed ownership matrix must classify each source
journal using at least `CODIGO_SISTEMA`, transaction references, source
movement IDs, journal type, date/cutoff, and links to migrated native entities:

| Disposition | Meaning |
|---|---|
| `NATIVE_ACCOUNTING` | Already represented by a migrated native product/client/provisioning transaction; do not import another journal |
| `DIRECT_GL_IMPORT` | No native target transaction owns the economic event; eligible for journal import after all account mappings resolve |
| `QUARANTINE` | Ownership, balance, reversal, account mapping, date, or source integrity is unresolved |

An exclusion based only on `CODIGO_SISTEMA` is insufficient because modules can
contain mixed historical paths and incomplete direct links. Classification
must be evidence-backed at journal level.

## Balance, status, and reversal rules

- A source journal must balance exactly after approved currency normalization.
- Empty headers are quarantined; they do not create zero-line target journals.
- A line with both debit and credit non-zero, both zero, an unresolved account,
  or an unsupported precision difference is quarantined unless a reviewed rule
  explicitly normalizes it.
- `ESTADO_PARTIDA` must be inspected and mapped before apply. Open/unposted
  source journals are not assumed eligible merely because they balance.
- Reversals must retain an explicit source-original/source-reversal
  relationship. Negating or dropping a journal without that relationship is
  prohibited.
- Annual-liquidation journals are ordinary December-numbered source journals
  but require their own accounting-ownership review before import.
- Back-period journals preserve their source period, source date, and exact
  `ref_num`; the engine must not silently rewrite them to appear current.

## Idempotency and write boundary

- Source identity is the complete four-column header key.
- The source hash covers the reviewed header fields plus ordered normalized
  detail lines.
- The target mapping records the generated `transaction_id`, target line IDs
  when available, source hash, plan, run, disposition, and reversal linkage.
- An unchanged source hash and reconciled target group produce `unchanged`.
- A changed source hash never silently edits posted accounting; it is
  quarantined pending an approved correction/reversal policy.
- Arissto access is read-only.
- Fineract writes must use the reviewed journal API unless a future contract
  explicitly authorizes a narrowly scoped, versioned extension. Direct ad-hoc
  inserts into `acc_gl_journal_entry` are not permitted by this scaffold.
- One journal is the atomic write/retry boundary. A run must never leave only
  the debit or credit side committed.

## Inspection and planning requirements

Inspection must report, without exposing sensitive descriptions:

- header and detail counts for the selected scope;
- duplicate full keys and duplicate line keys;
- balanced, unbalanced, empty, open/status-unknown, and reversal populations;
- unresolved and ambiguous GL-account mappings;
- exact `NUMERO_PARTIDA` null/blank/duplicate statistics;
- numbering-pattern exceptions without treating them as identity failures;
- native-accounting, direct-import, and unresolved ownership counts; and
- target accounting closures that would reject source dates.

Planning must require explicit source keys initially. Every planned item stores
its normalized source hash, ownership disposition, target account resolutions,
exact `ref_num`, line totals, and all readiness failures. No apply item may be
created for a quarantined or native-accounting journal.

## Reconciliation and acceptance

For every imported source journal, reconciliation must verify:

1. the crosswalk resolves to exactly one Fineract `transaction_id`;
2. all target lines in the group carry the exact source `ref_num`;
3. date, currency, accounts, debit/credit direction, and amounts match the
   normalized plan;
4. target debits equal target credits and equal source totals;
5. no second target group claims the same full source key; and
6. no native Fineract transaction duplicates the same economic event.

Acceptance requires a controlled local journal covering more than two lines,
an annual-liquidation example, a reviewed back-period example, a reversal
pair, an interrupted-response recovery test, an unresolved-account quarantine,
and an unchanged second plan. A full-period or production run remains blocked
until those cases pass and the product-accounting ownership matrix is approved.

## Open decisions

1. Final API or extension writer and lost-response recovery mechanism.
2. Durable crosswalk schema and whether it belongs in sync state, a versioned
   Fineract extension table, or both.
3. Complete journal-level ownership matrix across loan, savings, shares, cash,
   bank, vault, investments, mobile collections, internal operations, and
   accounting-origin journals.
4. Historical cutoff and ordering relative to native product migrations.
5. Reversal representation and immutable posted-journal correction policy.
6. Preservation fields for source period, type, module, close, state, and
   technical IDs beyond `ref_num`.
7. Currency and rounding behavior if future source data includes currencies or
   precision beyond the current reviewed population.
